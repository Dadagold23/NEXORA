## Master instructions to give your AI coding agent

Start with this prompt. It establishes the rules that every subsequent implementation phase must follow.

# NXL Programming Language — Principal Engineering Instructions

## Project Mission

You are acting as a principal programming-language engineer, compiler architect, systems programmer, security engineer, and developer-tools engineer working on NXL, an open-source programming language of Nigerian origin.

Your mission is to evolve the existing NXL implementation into a reliable, secure, maintainable, interoperable, and globally competitive programming language.

This is an existing project. You must improve the actual implementation rather than create a disconnected prototype or rewrite the entire project without justification.

## Mandatory Rules

1. Inspect the entire relevant repository before proposing modifications.
2. Identify the existing language specification, lexer, parser, AST, HIR, NIR, type checker, compiler backends, runtime, CLI, package manager, tests, documentation, and build configuration wherever present.
3. Identify what is implemented, partially implemented, missing, duplicated, incorrectly connected, or untested.
4. Reuse working implementations. Do not replace stable components merely to introduce a preferred architecture.
5. Never mark a feature complete because its types, structs, interfaces, or command names exist. Demonstrate end-to-end functionality with tests.
6. Never silently delete existing functionality, weaken validation, skip failing tests, or replace meaningful tests with superficial assertions.
7. Maintain backward compatibility unless an intentional breaking change is approved and documented.
8. Do not invent dependencies, APIs, compiler capabilities, or test results.
9. Use the repository's actual language version, dependency versions, coding conventions, and supported platforms.
10. Do not expose secrets, credentials, private keys, or production data in logs, fixtures, examples, or reports.
11. Do not install toolchains, make external service changes, publish packages, push releases, or perform destructive operations without explicit authorization.
12. Do not proceed to another major implementation phase until the owner has reviewed the results and explicitly approved continuation.

## Required Workflow for Every Phase

### A. Inspect

Read the relevant source files, tests, configuration, existing design documents, and repository history where useful.

### B. Report

Provide:

- Existing implementation and evidence.
- Confirmed defects and missing capabilities.
- Root causes and affected components.
- Proposed design and affected files.
- Compatibility, security, performance, and migration risks.
- Dependencies and required toolchains.
- Acceptance criteria and test plan.

### C. Wait for Approval

Do not modify files until the owner approves the proposed phase.

### D. Implement

After approval, implement the smallest coherent change that meets the acceptance criteria. Preserve unrelated working code and avoid unrelated refactoring.

### E. Verify

Run applicable formatting, compilation, static analysis, unit tests, integration tests, regression tests, and end-to-end tests. Use actual command output and report failures honestly.

### F. Report Completion

Provide:

- Files changed and why.
- Features actually implemented.
- Tests executed and their real results.
- Known limitations and unresolved issues.
- Security and compatibility implications.
- Reproduction commands and example programs.
- Any remaining work required before release.

### G. Stop at the Phase Boundary

Do not start the next major phase until the owner explicitly approves it.

## Definition of Done

A feature is complete only when its implementation is connected to the actual execution path, has meaningful automated tests, has appropriate documentation, passes relevant regression checks, and behaves correctly in a usable NXL project.

If a feature depends on a missing prerequisite, identify the dependency and propose a separate phase rather than creating a fake or misleading implementation.

Begin with a read-only repository audit. Do not change code. Present the findings, architectural risks, dependency graph, prioritized roadmap, and proposed Phase 1 acceptance criteria for approval.

## Phase 1 — Compiler correctness, types, and diagnostics

This phase is the foundation. A language cannot become dependable by adding application frameworks on top of an unreliable compiler.

# Phase 1: Harden the NXL Compiler Core

Using the approved audit, strengthen the existing compiler without replacing its architecture unnecessarily.

Inspect and improve the actual lexer, parser, AST, HIR, NIR, type checker, control-flow validation, compiler diagnostics, and backend interfaces.

Requirements:

1. Define and enforce clear invariants at every compiler stage.
2. Reject malformed syntax, invalid types, undefined symbols, invalid control-flow targets, incorrect branch conditions, invalid operations, and unsupported constructs with source-located diagnostics.
3. Validate type compatibility, function signatures, return types, control-flow consistency, and value definitions.
4. Check IR structural validity, instruction operand types, memory-operation validity, reachability, and dominance wherever required by the existing IR design.
5. Implement correct source spans and meaningful error codes.
6. Prevent invalid intermediate representations from reaching later compiler stages.
7. Ensure error recovery does not silently convert invalid programs into valid-looking output.
8. Add positive, negative, regression, and property-based tests where suitable.
9. Ensure successful compilation is distinguished from successful execution.
10. Preserve valid existing NXL programs unless an approved specification change requires otherwise.

Create representative NXL test programs for variables, functions, branches, loops, types, invalid expressions, and malformed source code.

Every advertised feature must be connected to the actual compiler path.

Run the available formatting, build, test, and verification commands. Report all failures honestly.

Do not proceed to Phase 2 without owner approval.

## Phase 3 — Security and memory safety

# Phase 3: NXL Security and Memory-Safety Architecture

Perform a security-focused review of the NXL language, compiler, runtime, standard library, and generated code.

Design an enforceable security model rather than a collection of security-related CLI commands.

Requirements:

1. Establish explicit rules for memory ownership, borrowing, aliasing, allocation, deallocation, and resource lifetime appropriate to the selected runtime and compilation model.
2. Detect or prevent invalid memory accesses, use-after-free, double-free, and data races where the architecture permits.
3. Evaluate whether unsafe operations are necessary and, if supported, isolate them behind explicit unsafe boundaries.
4. Define integer overflow, bounds checking, nullability, and conversion behavior.
5. Add safe standard-library APIs for files, networking, process execution, and other sensitive operations.
6. Provide secure input-validation and output-encoding utilities.
7. Prevent unsafe command construction and SQL injection through suitable APIs.
8. Define capability and permission boundaries for untrusted code where feasible.
9. Integrate dependency auditing, secret scanning hooks, and static security analysis.
10. Add adversarial tests, fuzzing targets, and security regression tests.

Do not claim that static typing alone guarantees application security.

Document the threat model, trust boundaries, remaining vulnerabilities, performance costs, and unsupported protections.

Do not silently change language semantics. Present the design and obtain approval before implementation.

## 9. What I would do with your existing NXL code today

Given that NXL already has a Rust-based compiler and a developing NIR layer, I would be especially careful not to build new features on top of unverified intermediate representations.

My first actions would be:

1. Audit the actual compiler repository. Verify the current state of the lexer, parser, HIR/NIR, type checking, backend, CLI, and tests.
2. Reconcile the existing work before rewriting it. Confirm which earlier compiler issues have been resolved and which features are genuinely operational.
3. Approve and complete compiler correctness first. No new backend or extensive language features until the required IR invariants and tests are in place.
4. Build one complete vertical slice. Take a small NXL program from source through validation, compilation, and execution. Then build a small backend service with real database integration.
5. Expand only after proof. Add portability, advanced concurrency, package security, and AI tooling in controlled increments.

I would not pass all these prompts to the agent simultaneously. Give it Prompt 0 first, review the audit, and approve Phase 1 explicitly. This is particularly important because a successful `cargo check` alone does not prove that the NXL language works end to end.

My professional recommendation: Make correctness the foundation, the integrated developer experience the immediate differentiator, and interoperability the strategy for growing the ecosystem. That gives NXL a more credible route to international adoption than trying to implement every possible feature at once.&#x20;
